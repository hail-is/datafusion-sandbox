All references are to datafusion-physical-plan v54.0.0, under src/aggregates/. Line numbers are approximate and drawn directly from the crate source.

0 · The big picture

Aggregation answers queries like SELECT k, SUM(v) FROM t GROUP BY k. The physical operator is AggregateExec. Conceptually it must, for every distinct group key, maintain some running state (a sum, a count, a hash set for DISTINCT, …) and emit one output row per group.

The naïve implementation is a hash table: group key → accumulator state, built up over the whole input, then drained at the end. That works but has one fatal property — it must hold every group in memory simultaneously, because any future row might belong to any group. For high-cardinality grouping this blows up.

The central idea of this document If the input is already sorted on the group keys (because some upstream operator produced that order, or an index provided it), then rows for a given group arrive contiguously. The moment you see a key change, every earlier group is provably finished — you can emit it and free its memory immediately. Aggregation becomes a streaming, bounded-memory operation. DataFusion detects this opportunity at planning time and exploits it at runtime through a small state machine called GroupOrdering.

The rest of this document builds up to that mechanism: first the operator and its modes, then the general hash engine, and finally the ordering machinery (§8–§12) that is the real subject of your study.

At execute() time, AggregateExec chooses one of three concrete stream implementations. Keep this fork in mind — everything later hangs off it.

3 · AggregateMode and the two-phase model

An aggregation is often split across partitions for parallelism. DataFusion models the phases with AggregateMode:

FinalPartialFinal valueMerges partial states from a single combined partition.
FinalPartitionedPartialFinal valueMerge when data was hash-partitioned by key, so each partition owns disjoint groups.

The input_mode() and output_mode() helpers (mod.rs:212–245) reduce each variant to two booleans: does it consume raw values or partial state, and does it produce final values or partial state? This is exactly what the engine checks to decide between calling update_batch vs merge_batch on accumulators (see §6).

parallel plan: the Partial→Final split exists for parallelism ┌─ part 0 ─┐ ┌─ part 1 ─┐ ┌─ part 2 ─┐ │ Partial │ │ Partial │ │ Partial │ each emits partial state per group └────┬─────┘ └────┬─────┘ └────┬─────┘ └──────────────┼──────────────┘ Repartition(by key) ──▶ groups land deterministically │ ┌────┴─────┐ │ Final │ merges partial states ──▶ final values └──────────┘
Why it matters for ordering The two-phase split is the reason emission semantics depend on mode: a Partial stage may freely emit early under memory pressure (downstream will merge anyway), whereas a Final stage cannot emit a group until it is sure no more partial state for it will arrive. This asymmetry shows up again in §13 (spilling).

4 · PhysicalGroupBy — keys & grouping sets

src/aggregates/mod.rs:265

pub struct PhysicalGroupBy {
    expr: Vec<(Arc<dyn PhysicalExpr>, String)>,       // the grouping expressions
    null_expr: Vec<(Arc<dyn PhysicalExpr>, String)>,  // NULL-typed stand-ins for GROUPING SETS
    groups: Vec<Vec<bool>>,                          // one null-mask per grouping set
    has_grouping_set: bool,                          // add the __grouping_id column?
}

A plain GROUP BY a, b has a single mask [false, false]. The other variants — GROUPING SETS, ROLLUP, CUBE — expand to several masks, and that expansion is what the rest of this section is about.

What grouping sets are, and why you'd want them

A GROUP BY normally computes aggregates at one level of detail. But reports often need several levels at once — a per-(region, product) total, plus a per-region subtotal, plus a grand total — and you'd like them in a single result set computed in a single pass over the data. That is what grouping sets give you. The three SQL forms are all sugar over an explicit list of sets:

SQLEquivalent grouping setsTypical use
GROUP BY GROUPING SETS ((a,b),(a),())literally those threeHand-pick exactly the levels you want.
GROUP BY ROLLUP(a, b)(a,b), (a), ()Hierarchical subtotals: detail → subtotal → grand total. Time drill-downs (year → month → day).
GROUP BY CUBE(a, b)(a,b), (a), (b), ()All 2n combinations — cross-tab / OLAP "slice and dice".

The empty set () is the grand total (group the whole input into one row). Semantically the query is equivalent to UNION ALL of one GROUP BY per set — but writing it as a grouping set lets the engine read the input once and fan each row into every set simultaneously, instead of re-scanning the (often expensive) input N times.

Concrete example 
SELECT region, product, SUM(sales)
FROM orders
GROUP BY ROLLUP(region, product);
produces one row per (region, product), plus one subtotal row per region (with product = NULL), plus one grand-total row (both NULL) — all from a single scan of orders.

How the planner represents them

src/aggregates/mod.rs:247 (doc comment)

The logical sets are flattened into the groups matrix: one boolean mask per set, where true means "this column is nulled out (not part of this set)". For GROUP BY GROUPING SETS ((a,b),(a),(b)) the planner builds:

expr      = [(col(a), "a"), (col(b), "b")]
null_expr = [(NULL, "a"), (NULL, "b")]    // NULL-typed stand-in for each column
groups = [
  [false, false],   // (a, b)   — neither nulled
  [false, true ],   // (a)      ≡ (a, NULL)
  [true , false],   // (b)      ≡ (NULL, b)
]

is_single() is just !has_grouping_set — the fast path. With grouping sets present, the operator carries one extra synthetic key column, __grouping_id (more on that below).

Runtime: one batch fanned into every set

src/aggregates/mod.rs:2183 (evaluate_group_by)

The expansion happens per input batch. evaluate_group_by evaluates the real expressions and the NULL stand-ins once, then assembles one set of group-key columns per grouping set — substituting the NULL array wherever the mask says true:

let exprs      = evaluate_expressions_to_arrays(group_by.expr, batch)?;       // real columns
let null_exprs = evaluate_expressions_to_arrays(group_by.null_expr, batch)?;  // all-NULL columns

group_by.groups.iter().map(|group| {
    let mut group_values = Vec::new();
    group_values.extend(group.iter().enumerate().map(|(idx, is_null)| {
        if *is_null { null_exprs[idx].clone() }   // column dropped from this set → NULL
        else        { exprs[idx].clone() }        // column active in this set
    }));
    if !group_by.is_single() {
        group_values.push(group_id_array(group, ordinal, max_ordinal, batch.num_rows())?);  // __grouping_id
    }
    Ok(group_values)
}).collect()   // → Vec<Vec<ArrayRef>>: one key-column-set per grouping set

The return type is the giveaway: Vec<Vec<ArrayRef>> — the outer vector has one entry per grouping set. Back in group_aggregate_batch (§6) the engine loops over these and calls group_values.intern(...) for each, so a single physical row contributes to every set's groups in the same hash table. A batch of R rows with S grouping sets effectively interns R·S logical rows.

The __grouping_id column: telling real NULLs from rolled-up NULLs

src/aggregates/mod.rs (group_id_array)

There's a subtlety. A subtotal row from set (a) has b = NULL because b was rolled up. But a genuine row might have b = NULL in the data. Worse, the key vector (a=5, b=NULL) could collide in the hash table across two different sets. The fix is a synthetic key column, __grouping_id, appended whenever has_grouping_set is true. It encodes which set a row belongs to, so different sets never share a group even when their visible key columns are identical:

// low n bits = the null mask itself; high bits = a "duplicate ordinal" tiebreaker
let semantic_id = group.iter().fold(0u64, |acc, &is_null| (acc << 1) | is_null as u64);
let full_id     = semantic_id | ((ordinal as u64) << n);
// width is chosen to fit: UInt8 / UInt16 / UInt32 / UInt64 (n + ordinal_bits ≤ 64)

The duplicate ordinal (high bits) handles the legal-but-odd case where the same set is listed twice (e.g. GROUPING SETS ((a),(a))); identical masks would otherwise produce identical ids. SQL's GROUPING(col) function reads this same id to report whether a column was aggregated away in a given row. Grouping sets are capped at 64 columns because the whole id must fit in a single 64-bit integer.

Carrying it through the Partial → Final split

src/aggregates/mod.rs (as_final)

Once a Partial stage has fanned rows into sets, the synthetic id must survive the merge so the Final stage keeps the sets distinct. as_final() rebuilds the group-by for the merge phase by promoting __grouping_id to an ordinary grouping column alongside the original keys, collapsing everything back to a single non-grouping-set GROUP BY over (a, b, __grouping_id). The fan-out already happened upstream; the final stage just merges partial states keyed by the explicit id.

Consequence for sort exploitation Because a single sorted input is replicated across sets with different columns nulled, no input ordering lines up with the keys of all sets at once. This is exactly why §8 filters out any column that is nulled in some set (groups.iter().all(|g| !g[idx])) and why the Sorted mode additionally requires group_by.groups.len() == 1. In practice grouping-set queries fall back to Linear (full hash aggregation) — they trade the streaming-emission optimization for single-pass multi-level output.

Per-batch processing: group_aggregate_batch

src/aggregates/row_hash.rs:923

Each input batch flows through three steps:

// 1. Map every row of the batch to a dense group index.
let starting_num_groups = self.group_values.len();
self.group_values.intern(group_values, &mut self.current_group_indices)?;
let group_indices = &self.current_group_indices;
let total_num_groups = self.group_values.len();

// 2. ◀ If new groups appeared, tell the ordering tracker. THIS is the hook
//    that lets a sorted input know a key boundary was just crossed.
if total_num_groups > starting_num_groups {
    self.group_ordering.new_groups(group_values, group_indices, total_num_groups)?;
}

// 3. Update each accumulator, indexed by group. Raw vs Partial decides the call.
if self.mode.input_mode() == AggregateInputMode::Raw && !self.spill_state.is_stream_merging {
    acc.update_batch(values, group_indices, opt_filter, total_num_groups)?;
} else {
    acc.merge_batch(values, group_indices, None, total_num_groups)?;
}
Vectorized, not row-at-a-time Note that intern and update_batch operate on whole columns. A batch of 8192 rows is hashed, interned, and folded into accumulator state in a handful of vectorized passes — there is no per-row virtual dispatch. GroupsAccumulator is the columnar accumulator interface that makes this possible.

The poll loop and early-emission hook

src/aggregates/row_hash.rs:725 (ReadingInput state)

After each batch is folded in, the stream asks the ordering tracker whether any groups are now safe to emit:

// only when not mid-spill: consult the ordering state machine
if (self.spill_state.spills.is_empty() || self.spill_state.is_stream_merging)
    && let Some(to_emit) = self.group_ordering.emit_to()      // ◀ §12
{
    if let Some(batch) = self.emit(to_emit, false)? {
        self.exec_state = ExecutionState::ProducingOutput(batch);
    }
    break 'reading_input;
}

For an unordered input emit_to() always returns None here, so output is produced only once the input is fully consumed — the classic full-materialization hash aggregate. For a sorted input it returns Some(EmitTo::First(n)) mid-stream, and the engine flushes n finished groups and frees them. That single conditional is the entire payoff of sort-order exploitation. We'll dissect it in §9–§12.

intern is the dense-indexer: it maps each row's group key to a stable integer, creating a new one for unseen keys. Those integers index both the stored keys and every accumulator's state — so the whole engine speaks in group indices, not key values.

Why emit(EmitTo::First(n)) needs cooperation

src/aggregates/group_values/row.rs:211 (GroupValuesRows::emit)

When the first n groups are flushed, every remaining group must be renumbered down by n so indices stay dense and contiguous (the accumulators do the same shift in lock-step). In the row-encoded implementation this is a HashTable::retain pass that drops entries below n and decrements the rest:

// remaining groups slide down: old index n → new index 0, n+1 → 1, ...
self.map.retain(|(_hash, group_idx)| {
    if *group_idx < n { return false; }   // emitted → drop
    *group_idx -= n;                          // kept → renumber
    true
});
The contract that makes streaming work GroupValues::emit, every accumulator's emit, and GroupOrdering::remove_groups must all apply the same EmitTo::First(n) shift. After the call, group n is the new group 0 everywhere. This three-way synchronization is what lets the engine drop finished groups mid-stream without corrupting the in-flight ones.

8 · ★ Detecting a usable sort order (planning time)

src/aggregates/mod.rs:779 (try_new_with_schema)

When an AggregateExec is constructed, it inspects the child's equivalence properties (which encode the child's sort orderings) and asks: how much of my GROUP BY can be satisfied by an existing ordering?

let input_eq_properties = input.equivalence_properties();
let groupby_exprs = group_by.input_exprs();

// Find the longest permutation of the GROUP BY exprs that the input is already sorted on.
// `indices` = positions (within groupby_exprs) of the columns covered by that ordering.
let (new_sort_exprs, indices) =
    input_eq_properties.find_longest_permutation(&groupby_exprs)?;

The key call is find_longest_permutation. Group-by columns are unordered as a set, so the input does not have to be sorted in the same order the user wrote the keys — any permutation of a prefix counts. The returned indices name the group-by columns that the existing order covers.

Two adjustments follow. First, grouping-set columns that are ever nulled are removed (recall §4 — a column that disappears in some grouping set can't anchor an ordering):

let indices: Vec<usize> = indices
    .into_iter()
    .filter(|idx| group_by.groups.iter().all(|group| !group[*idx]))
    .collect();

Then the verdict — the InputOrderMode (defined in src/ordering.rs:43):

let input_order_mode = if indices.len() == groupby_exprs.len()
    && !indices.is_empty()
    && group_by.groups.len() == 1                  // no grouping sets
{
    InputOrderMode::Sorted             // every group key is covered by the order
} else if !indices.is_empty() {
    InputOrderMode::PartiallySorted(indices)  // only a prefix is covered
} else {
    InputOrderMode::Linear             // nothing usable
};

10 · ★ GroupOrderingFull — the fully-sorted case

src/aggregates/order/full.rs

When the input is sorted on all group keys, group indices are produced in strictly increasing order: group 0's rows all arrive, then group 1's, then group 2's. So the rule is dead simple — the moment you see a higher group index, every lower index is finished. The whole tracker is a three-state machine holding a single integer:

enum State {
    Start,                         // no input yet
    InProgress { current: usize },   // `current` is the highest group index seen; can emit everything < current
    Complete,                      // input exhausted; emit everything
}

new_groups — just track the max index

pub fn new_groups(&mut self, total_num_groups: usize) {
    let max_group_index = total_num_groups - 1;
    self.state = match self.state {
        State::Start                  => State::InProgress { current: max_group_index },
        State::InProgress { current } => State::InProgress { current: max_group_index },
        State::Complete               => panic!("Saw new group after input was complete"),
    };
}

emit_to — flush everything before the current group

pub fn emit_to(&self) -> Option<EmitTo> {
    match &self.state {
        State::Start => None,
        State::InProgress { current } => {
            if *current == 0 { None }                 // still on the very first group
            else { Some(EmitTo::First(*current)) }   // groups 0..current-1 are done
        }
        State::Complete => Some(EmitTo::All),
    }
}

And remove_groups(n) simply does current -= n to stay aligned after a flush. The entire tracker is size_of::<Self>() bytes — O(1) state for unbounded input.

GROUP BY k, input sorted by k: EmitTo decisions as batches stream in batch 1: k = A A A B B interned indices 0 0 0 1 1 → current=1 → emit First(1) (flush group A) batch 2: k = B C C C D indices 1 2 2 2 3 → current=3 → emit First(3) (flush B, C) batch 3: k = D D E (EOF) indices 3 3 4 → input_done → emit All (flush D, E) at any instant only ONE group's state is held live.

11 · ★ GroupOrderingPartial — the partially-sorted case

src/aggregates/order/partial.rs

This is the subtle one. The input is sorted on a prefix of the keys only — e.g. grouping by (customer_id, state) with input sorted by state. Within a single state value, the customer_ids arrive in arbitrary order and may interleave, so we cannot finish a group the moment a new index appears (the way Full does). But when the sorted prefix value itself changes — say state goes 'MA' → 'MD' — every group belonging to the old prefix value is provably complete.

What it tracks

pub struct GroupOrderingPartial {
    // positions, within the group-by list, of the columns that ARE sorted.
    // grouping by (id, state) sorted on state ⇒ order_indices = [1]
    order_indices: Vec<usize>,
    state: State,
}

enum State {
    Taken,                          // transient (borrow-checker dance)
    Start,
    InProgress {
        current_sort: usize,           // smallest group index sharing the current sort-key value
        sort_key: Vec<ScalarValue>,    // the current sort-key value itself
        current: usize,                // highest group index seen so far
    },
    Complete,
}

Detecting the boundary — new_groups

The clever part: it projects the batch down to just the sorted columns, then uses Arrow's partition() to find the contiguous ranges where that sort key is constant. The start of the last range is where the newest sort-key value begins; that group index becomes the new current_sort.

// keep only the sorted (prefix) columns, then find runs of equal sort-key
let sort_keys = self.compute_sort_keys(batch_group_values);
let ranges = partition(&sort_keys)?.ranges();
let last_range = ranges.last().unwrap();

let range_current_sort = group_indices[last_range.start];
let range_sort_key     = get_row_at_idx(&sort_keys, last_range.start)?;

let (current_sort, sort_key) = if last_range.start == 0 {
    // no boundary INSIDE this batch — compare against the previous batch's key
    Self::updated_sort_key(current_sort, sort_key, range_current_sort, range_sort_key)?
} else {
    (range_current_sort, range_sort_key)   // boundary found in-batch
};

The cross-batch comparison handles a run that straddles batch edges:

fn updated_sort_key(current_sort, sort_key, range_current_sort, range_sort_key) {
    if let Some(sort_key) = sort_key {
        if compare_rows(&sort_key, &range_sort_key, &opts)? == Ordering::Equal {
            return (current_sort, sort_key);   // same value continues → no new boundary
        }
    }
    (range_current_sort, range_sort_key)        // value changed → boundary; advance current_sort
}

emit_to — flush groups belonging to earlier sort-key values

pub fn emit_to(&self) -> Option<EmitTo> {
    match &self.state {
        State::InProgress { current_sort, .. } => {
            if *current_sort == 0 { None }                    // still in the first sort-key run
            else { Some(EmitTo::First(*current_sort)) }      // everything before it is done
        }
        State::Complete => Some(EmitTo::All),
        _ => None,
    }
}
GROUP BY (id, state), input sorted by state: state | id | running group index ------+----+-------------------- MA | 10 | 0 ┐ MA | 20 | 1 ┘ sort-key 'MA' run → groups {0,1} MD | 10 | 2 ┐ ◀ sort key changed 'MA'→'MD': current_sort jumps to 2 MD | 30 | 3 ┘ ⇒ emit_to() = First(2) → flush groups 0,1 (all 'MA' groups) ... memory held live = only the groups of the CURRENT state value, not all (id,state) pairs.

State size is just the order_indices vector plus the one current sort_key — see size() at partial.rs:265. So memory is bounded by the number of distinct group keys sharing a single sorted-prefix value, no matter how many total groups the query produces.

12 · ★ EmitTo and the bounded-memory payoff

src/aggregates/order/mod.rs:57

GroupOrdering::emit_to() just dispatches to the active variant:

pub fn emit_to(&self) -> Option<EmitTo> {
    match self {
        GroupOrdering::None        => None,            // never emit early
        GroupOrdering::Partial(p)  => p.emit_to(),
        GroupOrdering::Full(f)     => f.emit_to(),
    }
}

EmitTo (from datafusion_expr) is the universal flush instruction understood by GroupValues and every GroupsAccumulator:

pub enum EmitTo {
    All,         // drain everything (used at end of input)
    First(usize), // drain the first n groups, keep & renumber the rest
}

When the stream receives Some(EmitTo::First(n)) it calls emit(...) (row_hash.rs:1103), which:

  1. pulls the first n group-key columns from group_values.emit(emit_to);
  2. calls group_ordering.remove_groups(n) to shift the tracker;
  3. appends each accumulator's output — evaluate(emit_to) for a Final stage, or state(emit_to) for a Partial stage / spill;
  4. builds the output RecordBatch and resizes the memory reservation downward.
The bottom line
OrderingPeak memoryFirst output appears
NoneO(total distinct groups)only after the input is fully consumed
PartialO(groups within one sorted-prefix value)as soon as the prefix value changes
FullO(one group window)almost immediately, streaming

13 · Spilling and the OOM paths

src/aggregates/row_hash.rs:78 (SpillState), 1031 (try_update_memory_reservation)

What happens when the order is not helpful (GroupOrdering::None) and the hash table outgrows the memory budget? After each batch the stream updates its MemoryReservation; on ResourcesExhausted it branches on an OutOfMemoryMode chosen at construction:

OutOfMemoryModeChosen whenAction
EmitEarlyPartial aggregationFlush accumulated groups downstream — a later Final stage will re-merge them, so partial early emission is always safe.
SpillFinal aggregation, unsortedSort current groups by key, write partial state to a temp file, clear memory, keep going.
ReportErrorFully sorted input, or no disk managerFail — but a sorted input shouldn't reach here, since it already streams in bounded memory.

The spill → re-merge trick

Spilling (row_hash.rs:1241) writes each spill sorted by the group keys. Once input is exhausted, the stream replaces its input with a StreamingMerge over the sorted spill files and re-runs aggregation in a second pass — and because the merged stream is now globally sorted on the keys, it sets:

self.spill_state.is_stream_merging = true;
self.group_ordering = GroupOrdering::Full(GroupOrderingFull::new());  // merged data IS sorted now
Nice symmetry The spill recovery path manufactures exactly the sorted-input condition from §10 and then rides the same GroupOrderingFull streaming machine to finish in bounded memory. Sorting is the unifying tool: either the input gives you order for free, or you pay to create it when you run out of RAM.

Under memory pressure with a Partial/Full ordering, oom_emit_to(n) (order/mod.rs:71) lets the engine flush up to n groups but clamps to the largest safe boundary the ordering allows, so early emission never violates correctness.

14 · The TopK and no-grouping paths (briefly)

No grouping — AggregateStream

src/aggregates/no_grouping.rs

With no GROUP BY, there is exactly one group. One Accumulator per aggregate folds in every batch (update_batch for raw input, merge_batch for partial), and at end-of-input a single output row is finalized. No interning, no ordering, no spilling — just a running fold.

TopK — GroupedTopKAggregateStream

src/aggregates/topk_stream.rs, src/aggregates/topk/priority_map.rs

For the pattern GROUP BY k ORDER BY MIN/MAX(agg) LIMIT k (single key column), DataFusion keeps only the best k groups in a PriorityMap — a hash map (key → slot) wired to a bounded heap of the top-k aggregate values. The crucial optimization is early discard:

fn insert(&mut self, row_idx) {
    if self.heap.is_worse(row_idx) { return; }  // heap full & this value can't make top-k → drop, no alloc
    ...
}

So a high-cardinality group-by that only needs the top 10 rows never materializes more than ~10 groups — O(k) memory instead of O(distinct groups). This is a different lever from sort order (it exploits the limit), but it shares the same spirit: avoid materializing groups you can prove you'll never output.

15 · Putting it together

A single SELECT k, agg(v) … GROUP BY k can run in any of these regimes; the planner and runtime pick based on the shape of the query and the order of the input:

AggregateExec::execute_typed │ ┌────────────────────────────┼──────────────────────────────┐ no GROUP BY? LIMIT k on agg? otherwise │ │ │ AggregateStream GroupedTopKAggregateStream GroupedHashAggregateStream (1 fold, 1 row) (PriorityMap, O(k) memory) │ ┌────────────────┴──────────────────┐ input_order_mode (decided in try_new, §8) │ ┌───────────────────────┬───────────────────────────┐ Linear PartiallySorted([..]) Sorted GroupOrdering::None GroupOrdering::Partial GroupOrdering::Full full hash table, emit on prefix-value emit on every new emit at end; change; O(groups per group index; spill / emit-early prefix value) O(1) streaming under memory pressure
The one thing to remember Sort-order exploitation is not a separate code path — it is the same hash engine, with a small state machine (GroupOrdering) deciding when a group is provably finished. Sorted input lets that decision happen mid-stream via EmitTo::First(n), converting an O(#groups)-memory blocking operator into an O(window)-memory streaming one. And when order isn't given, spilling sorts the data to recreate exactly that condition. Order is the lever; EmitTo is how it's pulled.
